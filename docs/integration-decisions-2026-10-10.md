# Integration decisions — October 10, 2026

## CopilotKit and Open Intelligent UI

Evaluated the [requested announcement](https://www.copilotkit.ai/blog/introducing-open-intelligent-ui), the linked [actual repository](https://github.com/CopilotKit/OpenIntelligentUI), and [official Strands quickstart](https://docs.copilotkit.ai/strands/quickstart). Source inspection is retained in task-2/copilot-*, ag-ui-strands-* and their GitHub tree snapshots.

The reference application uses Next.js/CopilotKit and a Python DeepAgents/LangGraph backend, with a separate visual-generation middleware and sandbox. Copying it would replace our Strands backend and introduce generated HTML/JavaScript. That is unnecessary for this proof slice. Official CopilotKit **does support Strands** through `ag_ui_strands` and an AG-UI HTTP agent; a controlled React frontend can run locally without hosted Intelligence.

The source bridge streams model text, tool arguments/results and state before the complete response has passed our release checks. Connecting it directly would expose unchecked content. A real integration needs a buffered release adapter: emit lifecycle progress only while the actual Strands tools run; publish a single accepted typed card/evidence result after deterministic grounding and Decisions; discard withheld text/tool payloads; correlate request and visitor identity; test cancellation/reset and failed review. Render only allowlisted React components. Never let client tools rewrite election scope or supply evidence.

Concrete next slice: add a local AG-UI endpoint around EvidenceLoop, a CopilotKit React provider/HTTP agent, and one measure component with accepted typed data; keep the existing default browser as fallback. Validate with the same COMBAT/NO/gap and stale-result tests before enabling live use. A full reference-app migration, generated sandbox or additional model is outside that slice. **Initial assessment, superseded for the controlled path:** CopilotKit was evaluated, not installed. See the later actual [controlled integration](copilotkit-local-integration.md); the generated Open Intelligent UI sandbox remains disabled. Current controlled cards and the ElevenLabs React orb must not be described as CopilotKit. No direction is selected from the design concepts; the common readability/source guidance is applied only.

## S3 and vectors

For the current bounded corpus, local indexed retrieval already resolves exact contest identities and enforces same-request reads, date/jurisdiction and source hashes. There are55 official passages plus four prepared candidate answers. An embedding store is not needed to prove this loop. S3 could later hold versioned originals; vectors could help retrieval across a larger reviewed corpus, but neither replaces scope checks, provenance or source review.

[Official S3 Vectors/Bedrock documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-bedrock-kb.html) describes ingestion, embedding and query permissions. Creating a Knowledge Base/vector index would require additional resources, ingestion/embedding spend and service-role permissions. The event account's Knowledge Base listing denial is preserved; do not route around it or use personal AWS resources. No bucket, index, Knowledge Base, service role or AgentCore resource was created. Bedrock Knowledge Base remains a preferred optional retrieval adapter when access is supplied; local retrieval keeps development moving.

## Mac audio and Pi display

Current backend/frontend share one listener: **127.0.0.1:8765**, Mac local HTTP only. There is no verified Pi-reachable LAN/HTTPS origin or running tunnel. Mac localhost can be a secure media context, while a Pi browser opened on Mac LAN HTTP cannot rely on getUserMedia. The Connect page's HTTPS does not change the remote browser's app origin. [Connect documents screen sharing, shell and clipboard](https://www.raspberrypi.com/documentation/services/connect.html), not USB/microphone redirection. [Media capture requires a secure context and permission](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia).

The current browser holds `epoch`, request sequence, abort controller, selection, answer and live session locally. The server returns caller-correlated request IDs but has no shared visitor/session registry, authenticated event channel or role pairing. **Opening two copies does not connect them.** Existing identity/reset logic can be reused, but a hybrid capture/display mode is not an existing feature.

Recommended order: first prove the Mac browser microphone and gated answer on the verified Mac input device after explicit capture permission. A direct USB-A data adapter remains the simplest Pi microphone route. Only if needed, build an explicit Mac capture client plus Pi display/controller, with one in-memory paired visitor session, short-lived random role tokens shown locally, no URL/query-token logging, accepted-answer events only, and a visible Mac armed/capturing state. Pi cannot silently arm the Mac; capture requires local consent. Reset/disconnect expires both roles, stops capture/output and rejects late events. Keep audio local to the Mac/provider path; the Pi needs approved text/state events, not raw audio redirection. No such channel is enabled now.
